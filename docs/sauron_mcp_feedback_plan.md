## 0. 피드백 출처와 한계

- **출처**: claude.ai 웹에 연결한 sauron MCP를 쓴 AI 에이전트의 자기 평가 1건. 질문은 "반도체·AI 관련 채용·대회 공지 찾기" 한 종류.
- **실측 (서버 로그, 22:55~22:56)**: 질문 1회에 요청 18건(연결 준비 3 + 도구 호출 15), 43초, 응답 합계 약 60KB. 동시 요청 최대 6건.
- **한계**
  - 세션 1개, 질문 1종이다. 다른 유형(학사 일정, 특정 학과 공지 등)에서는 문제의 우선순위가 달라질 수 있다.
  - 도구를 쓰는 AI의 관점이라 **"필드를 더 달라"는 쪽으로 기울어 있다.** 응답이 커질수록 대화에 쌓이는 비용도 커진다. 설계 원칙인 "설명은 충분히, 출력은 적게"와 부딪히는 제안이 있다.
  - 피드백이 매긴 난이도는 크롤러·운영 쪽 제약을 모르고 붙인 것이다. 아래에서 다시 평가했다.

|---|---|---|
| A. 출력량 | 질문 하나에 약 60KB. 기간을 90일로, 건수를 최대(40~50)로 잡은 brief 검색을 여러 번 했다 | 도구 설명에 "처음엔 좁게(기간·게시판), 부족하면 넓혀라"를 넣는다. 전후로 호출 수와 응답 바이트를 비교한다 |

| C. 측정 기준 | 개선 효과를 숫자로 비교할 기준선이 필요하다 | 기준 질문 몇 개를 정해 클린룸 서브에이전트로 돌리고 로그에서 (호출 수, 응답 바이트, 정답 여부)를 기록한다. 첫 기준선은 이번 세션(도구 호출 15회, 약 60KB) |

## 3. 개선 계획

### 1단계 — MCP 안에서만 (운영 중인 사우론에 영향 없음)

1. ✅ **검색**: 띄어쓰기 무시 매칭, `A|B` OR 검색 (#3). full 검색 평균 44ms
2. ✅ **중복 묶기** (#6)
   - 정규화 제목(공백·기호 제거)에서 **짧은 쪽이 긴 쪽 안에 통째로 들어 있으면** 같은 공지로 본다. 앞의 분류명(`[장학]`, `장학★`)과 뒤의 꼬리(`(~9/9까지)`, `홍보 요청`)를 모두 잡는다. 조건: 정규화 제목 12자 이상, 발견 14일 이내
   - 묶음 안의 **모든 제목과** 비교한다. 꼬리가 서로 다른 두 제목도 기본형 제목을 통해 같은 묶음에 들어간다(국가장학금 2차: 3묶음 → 18건 1묶음)
   - `also`는 `'dept_id:id'` 목록이다. 사본마다 내용이 다를 수 있어서(예: 마감 연장 재공지) 필요하면 그 사본을 열어 볼 수 있게 했다
   - 검증(2026-11-01): 포함 관계로 새로 묶이는 56개 조합과 큰 묶음 3개를 모두 확인했고 오병합은 없었다. 비용은 최악(150행)에 약 24ms
   - 남은 한계: 가운데에 말이 끼어든 변형(`고사건물 출입통제 안내` vs `고사건물 휴강(휴업) 및 출입통제 안내`)은 묶이지 않는다. 유사도 계산은 비용과 오병합 위험이 있어 쓰지 않는다
   - 참고: `id`는 사우론 DB가 매기는 번호(`notices.id`, AUTOINCREMENT)라 게시판이 달라도 겹치지 않는다. 사이트의 글 번호는 URL에만 있다
3. ✅ **시딩 공지 표시**: `status='seeded'`(이미 읽던 열이라 추가 부하 없음)면 `at=null`, `seeded=true`. 같은 순위 안에서는 시딩 공지를 뒤로 정렬한다. 최근 추가한 게시판의 옛 공지가 맨 위로 뜨던 문제도 함께 해결 (#4-1)
4. ✅ **일괄 상세 조회**: `get_notice(notice_ids=[…])` 최대 10건, 없는 id는 `missing` (#10)
5. ✅ **도구 설명**: OR·띄어쓰기 무시 사용법, `seeded`·`also` 필드 설명 추가. 정의 3,372 → 3,539자
   - **"좁게 시작해서 넓혀라"는 넣지 않기로 함** (2026-11-01 논의). 넓게 한 번에 찾을지 좁게 여러 번 찾을지는 토큰과 호출 수·지연 사이의 트레이드오프라 질문마다 다르다. 서버가 행동을 지시하지 않고 판단은 호출하는 모델에 맡긴다. 대안으로 상세도별 응답 크기 정보만 설명에 줄지는 결정 대기 (A)
6. ✅ **한도 조정**: IP당 순간 60·분당 120, 서버 전체 분당 600(순간 300), 동시 처리 32. 같은 IP는 같은 사람으로 본다 (B)
7. ⏳ **검증**: 기준 질문 3~5개를 클린룸 서브에이전트로 돌려 전후의 호출 수·응답 바이트·정답 여부를 비교 (C). 클라이언트가 새 도구 정의를 다시 불러온 뒤 진행

### 2단계 — 크롤러 쪽 (운영 중 서비스라 신중하게, 학과 단위로)

1. **제목 정제**: 전자정보공학부·전교 게시판의 `fetch_config` 수정 → `check` 모드로 확인 → 기존 제목 일회 정리(DB 백업 후) (#7)
2. **숫자 검사**: 텍스트 요약에 한해 날짜·시각 대조와 숫자 더듬기 패턴 검출 → 실패하면 재시도·승격, 그래도 실패하면 요약 의심 표시. 이미 쌓인 요약도 같은 검사로 의심 목록을 뽑아 `redo`로 다시 요약 (#2)

### 3단계 — 필요해지면

- 게시판별 실제 게시일 파싱 (#4-2)
- 첨부 링크 수집 (#5)
- 제목만 백필 (#8)
- "수집만" 모드 이후 외부 게시판 (#9)

### 보류

- 숫자 깨짐의 근본 해결 (#2) — 요약 모델(2B)의 능력 한계에 가깝다. 더 나은 모델로 바꾸기 전까지는 근본 해결이 어렵다 (2026-11-01 판단). #2의 좁은 검사(날짜·시각 대조)는 피해를 줄이는 보조 수단으로만 2단계에 남긴다.

## 4. 마감일 (#1) — LLM-as-Jev 방식 (2026-11-12)

### 설계

1. **날짜 후보**: 본문 + OCR 텍스트에서 정규식으로 뽑는다.
   - 형식: `2026.11.20.`, `11/20`, `11.20.(금)`, `11월 20일`, `~ 20일`, 뒤따르는 시각(`18:00`, `오후 5시`)
   - 연도 없는 날짜는 게시일에 가장 가까운 연도로 정한다(12월 공지의 `1/5` → 다음 해).
   - 게시일보다 이른 날짜는 뺀다. 후보가 0개면 LLM을 부르지 않고 `none`.
2. **선택**: 로컬 LLM에 원문 + 질문("학생이 지금 해야 하는 일의 마감일은 무엇인가?") + 기호 붙은 선택지(날짜 + 원문 36자, 마지막은 '해당 없음')를 준다.
   - `max_tokens=1`, `logprobs`로 첫 토큰(기호)의 확률을 읽는다. 생성이 없다.
   - 요약 직후 같은 프롬프트 뒤에 질문을 이어 붙인다 → llama-server가 본문 부분 KV 캐시를 재사용한다.
3. **판정**: 확률 0.8 미만이거나 호출 실패면 `unknown`, '해당 없음'이면 `none`, 그 외 `set` + 원문 날짜.
   - 날짜 값은 항상 원문에 있는 그대로다. LLM이 틀릴 수 있는 것은 '어느 날짜가 마감인가'뿐이다.

### 저장 · 표시

- DB: `notices.deadline_state`(set/none/unknown), `deadline_at`(KST, 날짜만이면 그날 끝까지), `deadline_conf`. 기존 DB에는 크롤러 시작 시 열을 붙인다(`Store._migrate`).
- 디스코드: `set`일 때만 요약과 AI 면책 문구 사이에 `⏰ <날짜> 까지 · <N일 후 / N일 전> 마감`.
  - 디스코드 타임스탬프(`<t:…:f>`, `<t:…:R>`)라 보는 사람 화면에서 저절로 바뀐다. **메시지를 수정하지 않는다.**
  - 없음·모름은 줄 자체를 뺀다.
  - 면책 문구 위에 두는 이유: 이 값도 로컬 LLM 판단이라 면책 범위에 들어가야 한다.
- MCP: `deadline` 필드(`set`만). 도구 설명·서버 지시문에 "소형 AI가 고른 값이라 틀릴 수 있다, 핵심이면 본문으로 확인" 문구.

### 실측

- 직접 만든 3건: 정답 3/3, 확률 0.991~0.999.
- 최근 실제 공지 30건(단독 프롬프트, 선택지 문맥 70자):
  - set 13건: 12건은 원문 문맥으로 보아 타당(신청·제출·불참 통보 마감). 1건(4016)은 날짜가 따로 떨어진 줄이라 문맥이 부족해 판단 불가 → 앞 줄을 붙이도록 고침.
  - none 10건: 후보 0개 3건(이미지에만 내용이 있는 공지 포함), 이미 끝난 모집(게시 전 마감), 신청 없는 행사 등.
  - unknown 7건: 확률 낮음 3건, 시간 초과(120s) 4건 → 제한을 300s로.
- 속도: 이 폰의 프롬프트 처리는 약 15토큰/s. 단독 프롬프트는 긴 공지에서 100s를 넘는다.
  - 요약 프롬프트를 재사용하면 본문은 캐시에서 온다(4007번: 1,684토큰 캐시, 질문 부분만 처리).
  - 남는 비용은 선택지 토큰이다(문맥 70자·11개 → 795토큰 ≈ 51s). 문맥을 36자로 줄였다.
- 2차(선택지 문맥 36자 + 날짜만 있는 줄은 앞 줄 붙임, 시간 제한 300s): 같은 30건. 시간 초과 4건이 모두 풀렸다(set). 중앙값 27s, 최대 185s(단독 프롬프트 기준).
  - 새로 드러난 오류: **행사·토론회의 '일시'를 마감으로 고름** (4018·4030). 게시판 머리글의 '등록일'도 후보로 섞임.
- 3차(질문에 "신청·접수·제출·등록·납부·회신 등 … 행사·설명회·시험이 열리는 일시 자체는 마감일이 아니다" 명시, 등록일·조회수 옆 날짜 제외): 행사 공지 5건 + 마감 있는 공지 7건 → **12/12 정답**. 행사 5건 모두 none(확률 0.998~1.0), 마감 7건은 기존과 같은 날짜(0.999~1.0).

### 남은 한계

- 확률이 높아도 틀릴 수 있다(검증 표본이 30건). 디스코드는 면책 문구 위에, MCP는 '100% 믿지 말 것' 문구와 함께 낸다.
- 이미 발송된 공지에는 표시되지 않는다(메시지를 수정하지 않는다는 원칙). 기존 공지의 DB 값을 채우는 일괄 작업은 따로 결정.
- 이미지에만 날짜가 있는 공지는 OCR이 돌아야 후보가 생긴다(크롤러 재시작 후).

- **운영 버그 (2026-11-21 발견·수정)**: 등록일 필터가 날짜 '뒤' 12자까지 봐서, 다음 줄에 '등록일'이 오는 취업 게시판 공지에서 진짜 마감이 후보에서 빠졌다. 모델은 남은 시작일을 골랐다(운영 set 81건 중 최소 3건: 4119·4242·4253). 날짜 '앞'만 보도록 고치고 회귀 테스트 추가. 크롤러 재시작 후 적용.
