작성: 2026-10-31 · 관련: [sauron_mcp_plan.md](sauron_mcp_plan.md) · 대상 코드: `mcp/` (MCP 서버), 일부는 크롤러

## 0. 피드백 출처와 한계

- **출처**: claude.ai 웹에 연결한 sauron MCP를 쓴 AI 에이전트의 자기 평가 1건. 질문은 "반도체·AI 관련 채용·대회 공지 찾기" 한 종류.
- **실측 (서버 로그, 22:55~22:56)**: 질문 1회에 요청 18건(연결 준비 3 + 도구 호출 15), 43초, 응답 합계 약 60KB. 동시 요청 최대 6건.
- **한계**
  - 세션 1개, 질문 1종이다. 다른 유형(학사 일정, 특정 학과 공지 등)에서는 문제의 우선순위가 달라질 수 있다.
  - 도구를 쓰는 AI의 관점이라 **"필드를 더 달라"는 쪽으로 기울어 있다.** 응답이 커질수록 대화에 쌓이는 비용도 커진다. 설계 원칙인 "설명은 충분히, 출력은 적게"와 부딪히는 제안이 있다.
  - 피드백이 매긴 난이도는 크롤러·운영 쪽 제약을 모르고 붙인 것이다. 아래에서 다시 평가했다.

## 2. 피드백에 없지만 같은 세션에서 드러난 것

| 항목 | 내용 | 조치 |
|---|---|---|
| A. 출력량 | 질문 하나에 약 60KB. 기간을 90일로, 건수를 최대(40~50)로 잡은 brief 검색을 여러 번 했다 | 도구 설명에 "처음엔 좁게(기간·게시판), 부족하면 넓혀라"를 넣는다. 전후로 호출 수와 응답 바이트를 비교한다 |
| B. 사용량 한도 | 같은 질문을 IP 하나로 보내는 클라이언트(Claude Code 등)라면 질문 1~2번에 IP당 한도 경계까지 간다. 동시 6건이 2명만 겹쳐도 동시 처리 한도(8)를 넘는다 | 제안값: IP당 순간 60·분당 120, 서버 전체 순간 200·분당 600, 동시 처리 32. **결정 대기** |
| C. 측정 기준 | 개선 효과를 숫자로 비교할 기준선이 필요하다 | 기준 질문 몇 개를 정해 클린룸 서브에이전트로 돌리고 로그에서 (호출 수, 응답 바이트, 정답 여부)를 기록한다. 첫 기준선은 이번 세션(도구 호출 15회, 약 60KB) |

## 3. 개선 계획

### 1단계 — MCP 안에서만 (운영 중인 사우론에 영향 없음)

1. ✅ **검색**: 띄어쓰기 무시 매칭, `A|B` OR 검색 (#3). full 검색 평균 44ms
2. ✅ **중복 묶기** (#6)
   - 정규화 제목(공백·기호 제거)에서 **짧은 쪽이 긴 쪽 안에 통째로 들어 있으면** 같은 공지로 본다. 앞의 분류명(`[장학]`, `장학★`)과 뒤의 꼬리(`(~9/9까지)`, `홍보 요청`)를 모두 잡는다. 조건: 정규화 제목 12자 이상, 발견 14일 이내
   - 묶음 안의 **모든 제목과** 비교한다. 꼬리가 서로 다른 두 제목도 기본형 제목을 통해 같은 묶음에 들어간다(국가장학금 2차: 3묶음 → 18건 1묶음)
   - `also`는 `'dept_id:id'` 목록이다. 사본마다 내용이 다를 수 있어서(예: 마감 연장 재공지) 필요하면 그 사본을 열어 볼 수 있게 했다
   - 검증(2026-11-01): 포함 관계로 새로 묶이는 56개 조합과 큰 묶음 3개를 모두 확인했고 오병합은 없었다. 비용은 최악(150행)에 약 24ms
   - 남은 한계: 가운데에 말이 끼어든 변형(`고사건물 출입통제 안내` vs `고사건물 휴강(휴업) 및 출입통제 안내`)은 묶이지 않는다. 유사도 계산은 비용과 오병합 위험이 있어 쓰지 않는다
   - 참고: `id`는 사우론 DB가 매기는 번호(`notices.id`, AUTOINCREMENT)라 게시판이 달라도 겹치지 않는다. 사이트의 글 번호는 URL에만 있다
3. ✅ **시딩 공지 표시**: `status='seeded'`(이미 읽던 열이라 추가 부하 없음)면 `at=null`, `seeded=true`. 같은 순위 안에서는 시딩 공지를 뒤로 정렬한다. 최근 추가한 게시판의 옛 공지가 맨 위로 뜨던 문제도 함께 해결 (#4-1)
4. ✅ **일괄 상세 조회**: `get_notice(notice_ids=[…])` 최대 10건, 없는 id는 `missing` (#10)
5. ✅ **도구 설명**: OR·띄어쓰기 무시 사용법, `seeded`·`also` 필드 설명 추가. 정의 3,372 → 3,539자
   - **"좁게 시작해서 넓혀라"는 넣지 않기로 함** (2026-11-01 논의). 넓게 한 번에 찾을지 좁게 여러 번 찾을지는 토큰과 호출 수·지연 사이의 트레이드오프라 질문마다 다르다. 서버가 행동을 지시하지 않고 판단은 호출하는 모델에 맡긴다. 대안으로 상세도별 응답 크기 정보만 설명에 줄지는 결정 대기 (A)
6. ✅ **한도 조정**: IP당 순간 60·분당 120, 서버 전체 분당 600(순간 300), 동시 처리 32. 같은 IP는 같은 사람으로 본다 (B)
7. ⏳ **검증**: 기준 질문 3~5개를 클린룸 서브에이전트로 돌려 전후의 호출 수·응답 바이트·정답 여부를 비교 (C). 클라이언트가 새 도구 정의를 다시 불러온 뒤 진행

### 2단계 — 크롤러 쪽 (운영 중 서비스라 신중하게, 학과 단위로)

1. **제목 정제**: 전자정보공학부·전교 게시판의 `fetch_config` 수정 → `check` 모드로 확인 → 기존 제목 일회 정리(DB 백업 후) (#7)
2. **숫자 검사**: 텍스트 요약에 한해 날짜·시각 대조와 숫자 더듬기 패턴 검출 → 실패하면 재시도·승격, 그래도 실패하면 요약 의심 표시. 이미 쌓인 요약도 같은 검사로 의심 목록을 뽑아 `redo`로 다시 요약 (#2)

### 3단계 — 필요해지면

- 게시판별 실제 게시일 파싱 (#4-2)
- 첨부 링크 수집 (#5)
- 제목만 백필 (#8)
- "수집만" 모드 이후 외부 게시판 (#9)

### 보류

- 마감일 필드 (#1), 숫자 깨짐의 근본 해결 (#2) — 요약 모델(2B)의 능력 한계에 가깝다. 더 나은 모델로 바꾸기 전까지는 근본 해결이 어렵다 (2026-11-01 판단). #2의 좁은 검사(날짜·시각 대조)는 피해를 줄이는 보조 수단으로만 2단계에 남긴다.
