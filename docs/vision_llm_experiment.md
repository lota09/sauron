# 온디바이스 LiteRT 멀티모달 LLM 성능 시험

**대상 시스템**: sauron_reborn (숭실대 학과공지 온디바이스 알림 봇)
**모델/런타임**: Gemma-4-E2B-it @ OlliteRT(LiteRT-LM backend), OpenAI 호환 `/v1/chat/completions`, 스트리밍, greedy(결정론)
**시험 목적**: 본문 없이 이미지로만 내용을 전달하는 공지(제목O·본문X·그림O)를 OCR 대신 **멀티모달 LLM**으로 요약할 수 있는지, 그 성능·정확도·실패양상을 계측
**작성일 기준**: 2026-07 (세션 실측 로그 기반)

---

## 초록

정규 텍스트가 없는 이미지 공지를 온디바이스 2B 멀티모달 LLM으로 요약하는 실험을 수행했다. 비전 입력이 **동작함은 확인**되었으나, 정확도는 실서비스 신뢰 기준에 못 미쳤다: 상품 브랜드 환각(即席みそ汁→"나이키"), 상온/냉장 오독, 공지 날짜·요일 오독, 유의사항 환각이 관측됐다. 또한 한 시행에서 **반복붕괴(degeneration)** 가 발생했고, **프롬프트를 1회 미세 변경**하자 붕괴 없이 정상 출력으로 전환됐다 — 이는 greedy 결정론 하에서도 입력의 미세 변형이 유의미한 재시도(리롤)임을 실증한다. 성능은 이미지당 총 50–60초(이미지 인코딩 4.7–6.3초, 디코딩 ≈5 tok/s)로, 10분 주기·저빈도 신규라는 본 시스템 특성상 수용 가능하다. 결론적으로 비전은 **"없는 것보다 나은 best-effort 구제 경로"** 로 채택하되, 결정론적 검증기(반복붕괴 제거·언어이탈 차단)와 면책 문구를 반드시 병행한다.

---

## 1. 배경

sauron_reborn의 요약 파이프라인은 `크롤 → (본문/OCR) → LLM 요약 → 디스코드 발송`이다. 일부 공지는 포스터 이미지가 본문을 대체하여 텍스트 추출이 불가능하다. 기존 설계는 이 경우를 `no_content`("요약할 내용이 없습니다")로 처리했다. 온디바이스 LLM이 비전을 지원함이 확인되어, OCR을 켜지 않고도 이미지에서 직접 요약을 시도할 수 있는지 검증한다.

## 2. 실험 설정

- 엔드포인트: `POST /v1/chat/completions`, `model=Gemma-4-E2B-it`, `stream=true`, `max_context_tokens=15000`.
- 입력: OpenAI 멀티모달 형식 `content:[{type:text}, {type:image_url, image_url:{url:"data:image/...;base64,..."}}]`.
- 시료 2종:
  - **S1** 즉석 미소국(即席みそ汁) 포장지 사진, JPEG ≈ 3.5 MB (일본어, 반사·곡면 있음).
  - **S2** "2026-2학기 추가학기 학점등록 안내" 공지 이미지, PNG ≈ 253 kB (한국어, 표 포함, 정연한 폰트).
- 시행:
  - **A** = S1 + 프롬프트 "이건 뭐야? 어떻게 먹는거야?"
  - **B1** = S2 + "이미지가 전달하고자 하는 내용을 최대한 자세하게 서술"
  - **B2** = S2 + "다음 이미지에 나타난 내용을 자세하게 서술"

## 3. 결과

### 3.1 성능 지표

| 시행 | 이미지 | TTFB(인코딩) | prefill | decode | 출력토큰 | 총 지연 | 결과 |
|---|---|---|---|---|---|---|---|
| A | 3.5 MB (1장) | 6.31 s | 0.63 tok/s | 5.30 tok/s | 251 | 53.7 s | 오답(환각) |
| B1 | 253 kB (1장) | — | — | — | (절단) | — | 반복붕괴 |
| B2 | 253 kB (1장) | 4.72 s | 1.06 tok/s | 5.05 tok/s | 283 | 60.8 s | 대체로 정확 |
| C | 253 kB + 303 kB (2장) | 8.41 s | 0.59 tok/s | 6.26 tok/s | 510 | 89.9 s | 오답, 이미지 수 3장 오인 |
| D | 303 kB + 253 kB (2장) | 8.42 s | 0.12 tok/s | 5.89 tok/s | 398 | 76.0 s | 오답, 이미지 수 **2장 정확** |

- **C·D (다중 이미지)**: 전송 포맷은 `content` 배열에 `image_url`을 여러 개 넣는 것으로 확인. C(프롬프트 "…자세히 서술")는 2장을 3장으로 오인했으나, D(프롬프트 "이거 요약", 순서 반전)는 **2장을 정확히 2장으로 서술**. → **이미지 수 환각은 재현 불안정한 모델 노이즈이며 입력 이미지 수·크기와 직접 인과가 아니다.** 인코딩 8.4초(2장), 출력 398~510토큰, 총 76~90초.

- `prefill`의 낮은 값은 착시다: 텍스트 토큰이 4–5개뿐이라 `prompt_ms`(4.7–6.3초)의 대부분이 **이미지 인코딩 시간**이다. 즉 비전의 고정비용 = **TTFB ≈ 5–6초**.
- 디코딩은 텍스트 요약과 동일한 ≈5 tok/s. 총 지연은 출력 길이에 비례(250–280 토큰 → 47–56초).
- 이미지 크기(3.5 MB vs 253 kB)는 총 지연에 큰 영향 없음 — 인코더가 고정 해상도로 정규화하므로 **전송·다운스케일만 이득**. → 전송 전 다운스케일 권장.

### 3.2 정확도 분석

**A (미소국 포장지) — 심각한 오답.**
- 브랜드 환각: 제조사 ハナマルキ(Hanamaruki)를 "**나이키(ナイキ)**"로, 품목 即席みそ汁(즉석 미소된장국)을 "건강 보조 식품"으로 오인.
- 보관 오독: 常温保存(상온)을 "냉장 보관"으로.
- 부분 정답: 내용량 7.5g, 賞味期限 2026.06.30.
- 핵심 식별 실패 → 사용자에게 잘못된 정보를 권위 있게 전달할 위험.

**B2 (공지) — 골격은 정확, 세부는 불신.**
- 정답: 제목, "정규 8학기 후 추가 이수" 취지, 대략적 일정 축(8.8~8.14, 8.10~8.14, 8.20, 8.31, 9월 납부).
- 오류: 사유를 "취업준비·복학·계절학기"로 환각(실제=졸업학점 부족·교직 이수·재수강); 8.8**(토)**→(수), 8.10**(월)**→(일) 요일 오독; 납부일 9.2~9.4를 "9.9(금)"으로; **등록금 분할표(1/6·1/3·1/2·전액) 누락**; 유의사항 일부 환각.

→ **구조·요지는 잡지만, 날짜·수치·목록 같은 정밀 필드는 신뢰 불가.** 이전에 텍스트 요약에서 내린 결론("2B는 정밀 필드 검증 불가")이 비전에서도 동일하게 재확인된다.

## 4. 논의

### 4.1 반복붕괴와 결정론적 구제
B1은 제목·앞부분을 맞춘 뒤 동일 문장("…등록금 납부 기한을 준수해야 합니다.")을 약 60회 반복하는 붕괴에 빠졌다. 본 시스템의 `strip_degenerate`(동일 줄/짧은 토큰 반복 절단)에 이 출력을 통과시키면 **63줄 → 5줄로 절단되어 앞부분이 유효 요약으로 살아난다**(검증 통과 확인). 즉 붕괴는 코드로 흡수 가능하다.

### 4.2 프롬프트 민감도 = 리롤의 실증
B1(붕괴)과 B2(정상)는 **같은 이미지·같은 모델**에 프롬프트만 미세하게 다르다("최대한 자세하게 서술" vs "다음 이미지에 나타난 내용을 자세하게 서술"). greedy 결정론에서 동일 입력은 동일 출력이지만, 입력이 몇 토큰만 달라져도 이후 로짓 분포가 바뀌어 결과가 붕괴↔정상으로 갈렸다. 이는 재시도 정책에서 채택한 **"검증 실패 시 프롬프트 미세 변형 후 재시도(리롤)"** 의 타당성을 실측으로 뒷받침한다.

### 4.3-b 다중 이미지: 지원 + 개수 상한
포맷(`content` 배열 내 다중 `image_url`)은 동작한다. 개수 환각(C)은 D에서 재현되지 않아 **모델의 간헐적 노이즈**로 판단하며, 이미지 수·크기와 직접 인과는 아니다. 다만 정확도 자체는 단일 이미지와 마찬가지로 낮고(정밀 필드 신뢰 불가), 이미지가 늘면 지연·출력이 커져 붕괴 위험이 오른다. → **다중 이미지를 지원하되 개수/크기로 상한**을 둔다(§4.3-c).

### 4.3-c 이미지 수용량(컨텍스트 예산)
- Gemma 3/3n 비전은 이미지 1장을 **고정 소프트토큰 ≈ 256개**로 인코딩(SigLIP/MobileNet → 256 풀링). 크고 세로긴 이미지는 **Pan-and-Scan** 분할로 2~4 크롭(512~1024토큰)이 될 수 있음.
- 컨텍스트 15,000 = 텍스트입력 + 이미지토큰 + 출력. 출력 예약 2048 + 텍스트 ~300 → **이미지 예산 ≈ 12,650토큰**.
- 256/장 → **~49장**, 768/장(PaS) → **~16장**, 1024/장 → **~12장**. **컨텍스트는 병목이 아니다(십수 장 여유).**
- 실제 상한은 **지연·품질**: 인코딩 ~4초/장 + 출력 폭증(디코딩 ~5tok/s)·붕괴 위험. → 채택: **최대 4장**(`LLM_VISION_MAX_IMAGES`, 어떤 PaS에도 ≤~4k토큰으로 안전, 인코딩 ~16초), 각 장 1024px 다운스케일(PaS 크롭·전송 절감). 4장 초과 공지는 앞 4장만.

### 4.3-d OCR-텍스트 파이프라인 vs 비전 (정확도 비교)
같은 이미지 공지를 (a) 비전 LLM 직접 vs (b) OCR→텍스트→(기존 텍스트 요약기)로 처리할 때:
- **비전 LLM**: 레이아웃·표를 암묵 처리, 추가 설치 불필요(LLM 재사용). 단점(실측): **사실 환각**(브랜드/날짜/'합격등록' 등 없는 내용을 지어냄), 느림(50~90초), 개수 오인. 실패양상이 "통째로 지어내기"라 위험.
- **Tesseract(kor)**: 경량·ARM/proot 친화·빠름(~1~3초/장)·결정론. 깔끔한 인쇄 한글엔 준수하나 **표/다단·사진·곡면엔 약함**(미소국 포장지류는 사실상 실패). 그러나 **실제 추출 텍스트**를 기존 요약기(붕괴제거·언어검증·리롤 방어선 보유)에 넘기므로 요약기가 없는 사실을 지어내지 못함 → 실패양상이 "글자 단위 오독"으로 국소적. **초저비용 철학에 최적합.**
- **PaddleOCR**: CJK 정확도·표 구조인식(PP-Structure) 우수 → 정확도는 최상. 단 **무겁다**(설치·RAM·CPU 부담, 폰/proot/무외부의존 철학과 상충). Note20 RAM 제약에서 부담.
- **평가**: 대상이 대체로 **깔끔한 인쇄 한글 공지**이므로, 사실 충실도는 **OCR→텍스트→LLM이 비전보다 높을 가능성이 크다**(요약기가 픽셀이 아니라 실제 텍스트를 요약 → 통째 환각 없음). 다만 표·사진은 OCR도 약함. **권장 방향 = 하이브리드**: OCR을 먼저 시도해 텍스트가 충분하면 텍스트 요약(정확·빠름), OCR 텍스트가 빈약하면(그래픽/사진) 비전으로 폴백. 엔진은 **Tesseract 기본(경량), Paddle는 정확도 필요 시 선택**.

### 4.3 정확도-비용 트레이드오프
2B 비전의 정밀 정확도는 낮지만, 대상은 "이미지밖에 없어 원래 요약이 불가능하던" 공지다. 대안이 `no_content`(무요약)이므로, **면책 문구를 단 best-effort 요약이 무요약보다 사용자 효용이 크다**(단, 오답 위험을 면책 문구가 상쇄). 정밀 정보는 항상 원문 링크로 확인하도록 유도한다.

## 5. 시스템 반영(코드)

- `summarize/llm.py`: 생성 루프를 `messages` 기반으로 리팩터하고 `summarize_vision(title, image_url)` 추가(텍스트 요약과 재시도·검증·리롤 로직 공유). 반환 engine=`vision:<model>`.
- `summarize/vision.py`(신규): 이미지 URL → (Pillow 있으면 `LLM_VISION_MAX_PX` 이하 다운스케일 후) base64 data URL. 실패 시 `None`.
- `summarize/worker.py`: 본문·OCR 공백이면 `EmptyContentError` → **이미지가 있으면(최대 `LLM_VISION_MAX_IMAGES`장) 비전으로 구제**, 그마저 없거나 로드 실패면 `no_content`.
- `config.py`: `LLM_VISION`(기본 True), `LLM_VISION_MAX_PX`(1024), `LLM_VISION_MAX_IMAGES`(4), `LLM_VISION_PROMPT`.
- `summarize_vision(title, image_urls)`: 1~N장 data URL 리스트 수용, engine=`vision:<model>×N`.
- 기존 방어선 그대로 적용: `strip_degenerate`(붕괴), 언어이탈 검증, 리롤 재시도, 성공 시 면책 문구, 실패 시 `fail_reason` DB 기록.

## 6. 결론 및 향후 과제

온디바이스 2B 비전은 **기능적으로 동작하고 반복붕괴·언어이탈은 기존 결정론 방어선으로 흡수 가능**하나, **정밀 사실(날짜·수치·목록)은 신뢰 불가**하다. 따라서 이미지 대체 공지에 한한 **best-effort 구제 경로**로 채택하고 면책 문구를 필수화한다.

향후 과제:
1. **다운스케일 효과 계측** — 512/768/1024 px에서 지연·정확도 곡선.
2. **프롬프트 최적화** — 붕괴 저감·정밀도 향상 프롬프트 탐색(자세히-서술형 vs 개조식-요약형).
3. **폴백 모델(E4B) 비교** — 동일 시료에서 정확도/지연 차이.
4. **핵심 필드 결정론 보강** — 날짜는 정규식 등 코드로 교차검증(비전 산출 날짜 신뢰 금지).
5. **다중 이미지 공지** — 최대 4장 동시 전송 지원(§4.3-b/c). 개수 환각은 간헐적 모델 노이즈. 향후: 장수↑ 시 "장별 개별 요약→병합"이 단일 요청보다 정확할지 비교.
6. **OCR 하이브리드** — §4.3-d 결론대로 OCR(Tesseract 기본) 먼저, 텍스트 빈약 시 비전 폴백 구조를 실측 비교 후 도입 검토.
