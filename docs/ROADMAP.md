# sauron_reborn 확장 로드맵 (나중에 할 것)

MVP(크롤→요약→디스코드 알림 + 구독봇) **이후**에 검토할 대형 확장 기능 목록.
현재 배포 전 남은 작업은 [`STATUS.md`](STATUS.md) 참고 — 이 문서는 "그 다음" 이야기다.

설계 철학 재확인(평가 기준): **초저비용 · 무외부의존 · 온디바이스 단일기기 · 누락 0 · 완전한 시스템 통제.**
확장 기능은 이 철학과 충돌할 수 있으므로, 각 항목을 *철학 충돌 여부*까지 포함해 평가한다.

## 보안 프레이밍 — inbound vs outbound (모든 항목의 전제)

세 기능의 리스크 차이는 대부분 **"폰이 인바운드 연결을 받느냐"** 하나로 갈린다. 이게 핵심이다.

- **인바운드 서빙(API·동적 RSS)**: 폰이 포트를 열고 외부 요청을 받는다 → **폰 IP/포트가 공개** → 스캐닝·DDoS·자원고갈의 표적. 배터리 기기라 자원고갈에 특히 취약. 홈 NAT 뒤라면 포트포워딩(홈 IP 노출) 또는 터널(외부 의존)이 필요. **사용자가 지적한 리스크가 바로 이것이며, 타당하다.**
- **아웃바운드만(디스코드 봇·정적 푸시)**: 폰이 **바깥으로만** 연결한다(디스코드 게이트웨이에 접속 / 정적 호스트에 결과 업로드). **인바운드 포트 0 → 폰 IP 비공개 → 스캔·DDoS 표적이 되지 않음.** 현재 알림봇이 게이트웨이(아웃바운드)를 쓰는 이유가 이거다.

역설적 요약: **API/RSS(자가 서빙)는 IP 리스크 최대·컴퓨트 리스크 최소**, **AI 봇은 IP 리스크 0·컴퓨트 리스크 최대.** 그래서 완화 전략도 정반대다.

완화 사다리(인바운드가 불가피할 때, 위에서부터 선호):
1. **인바운드를 아예 안 받는다** — 결과를 정적 파일로 만들어 무료 정적/엣지 호스트(GitHub Pages·Cloudflare Pages·객체스토리지)에 **push**. 폰은 아웃바운드만. 공격 표면 0, CDN 캐시, 무료.
2. **Cloudflare Tunnel 등 리버스 터널** — 오리진 IP 은닉 + WAF/DDoS 방어(무료 티어). 단 외부 의존 + 계정 발생(철학과 약한 충돌).
3. 최소한 **읽기전용 + 레이트리밋 + 캐시 + 응답에 비밀정보 없음**.

## 1. API 호스팅 — 학과별 최신 공지 조회 API

**개요:** REST 엔드포인트로 "특정 학과의 최신 공지 N건"(제목·링크·요약·날짜 등)을 JSON으로 반환. DB(SQLite)를 읽어 응답.

**가치:** 3rd-party 통합의 토대. RSS·AI봇·외부 웹/앱이 전부 이걸 소비할 수 있음. 데이터가 이미 DB에 정규화돼 있어 재사용성이 큼.

**구현비용:** 낮음(읽기전용). 다만 `무외부의존` 철학상 stdlib `http.server`로 짜면 기능이 빈약하고, FastAPI/Flask를 쓰면 의존성이 는다. 라우팅·페이지네이션·캐시 정도.

**리소스요구:** 낮음(읽기전용·경량). 단 **상시 인바운드 리슨**이 폰 안정성·배터리에 부담.

**리스크(높음, IP 축):**
- 폰 IP/포트 공개 → 스캔·DDoS·자원고갈(사용자 지적대로).
- 홈 NAT 뒤 → 포트포워딩(홈 IP 노출) 또는 터널(외부 의존) 필요.
- 쿼리 파라미터가 있으면 주입·남용 표면도 생김(읽기전용이라 경미하나 0은 아님).

**완화:** 위 사다리 1순위(**정적 JSON 스냅샷 push**)로 바꾸면 대부분 해소 — 크롤 주기마다 `/{dept}/latest.json` 같은 파일을 만들어 무료 정적 호스트에 올리면 "API처럼 읽히되 인바운드 0". 진짜 동적 질의(임의 필터·검색)가 필요할 때만 터널+레이트리밋+읽기전용으로.

**평가:** 가치 中, 구현 低, **리스크 高(자가 동적 서빙 시)**. → **동적 자가호스팅은 비권장.** 필요하면 정적 스냅샷 형태로. 우선순위 中하.

## 2. RSS 호스팅 — 학과별 최신 공지 구독

**개요:** 학과별 최신 공지를 RSS/Atom 피드(XML)로 노출 → 임의의 RSS 리더로 구독.

**가치:** 표준·범용(모든 RSS 리더). 디스코드에 묶이지 않는 구독 채널을 무료로 추가. 유지보수 거의 0.

**구현비용:** 매우 낮음. RSS는 **본질적으로 정적 파일** — 크롤 때마다 학과별 XML을 재생성만 하면 됨. 동적 서버 불필요.

**리소스요구:** 매우 낮음(정적 파일 쓰기).

**리스크(낮음 — 정적 배포 시):** RSS는 정적이라 위 사다리 1순위와 완벽히 맞는다. 크롤 결과를 XML로 렌더 → **무료 정적 호스트에 push** → 폰은 아웃바운드만, **공격 표면 0, IP 비공개, CDN 캐시**. 사용자의 IP 노출 우려를 구조적으로 회피. (약한 외부 의존은 생기지만 "인바운드 서빙"이 아니라 "결과 업로드"라 시스템 통제 훼손이 작다.)

**평가:** 가치 中상, 구현 低, **리스크 低.** → **세 기능 중 가성비·안전성 최고. 확장 1순위 추천.** 정적 푸시로만 하고 폰에서 동적 서빙하지 말 것.

## 3. 학과 공지 AI 에이전트 디스코드봇 — 대화형 개인화 안내

**개요:** 디스코드 봇에게 관심사·상황(예: "3학년 SW, 데이터 공모전 있어?", "이번 주 마감 장학금")을 물으면, 수집된 공지에서 검색·추론해 맞춤 답변. 리소스 부담이 커서 **일일 사용량 제한/후원자 전용** 기능 포함.

**가치:** 높음(개인화·차별화). 단방향 알림을 넘어 "질문하면 답한다"는 상호작용.

**구현비용:** 높음. 필요한 것: (a) 공지 검색(관심사→관련 공지 매칭, 이상적으로는 임베딩 기반 RAG — 모델·메모리 추가), (b) 질의마다 LLM 생성(온디맨드·대화형), (c) 사용량 쿼터·후원 게이팅(사용자별 카운트·역할 티어).

**리소스요구(높음 — 컴퓨트 축):**
- 온디바이스 2B LLM은 질의당 ~50~90초 + **단일 슬롯**이라 동시 사용자가 큐잉 → 대화형 UX엔 치명적 지연.
- RAG용 임베딩 모델을 얹으면 폰 메모리가 또 겹침(요약 LLM과 경합).

**리스크:**
- **컴퓨트 남용/고갈** — 질의마다 LLM. 스팸이 단일 슬롯·배터리를 소진 → 알림봇 요약까지 지연. 그래서 **쿼터/후원 게이팅이 선택이 아니라 필수**.
- **품질** — 2B가 RAG+추론으로 마감·대상·자격을 다루면 오독/환각 위험. 마감일 오답은 고위험. (기존 면책문구 + 원문 링크로 완화하되 한계 명확.)
- **IP 리스크는 0** — 디스코드 게이트웨이(아웃바운드)라 폰 포트를 안 연다. 이 점은 API/RSS보다 유리.

**완화:** 사용자별 일일 쿼터 + 백프레셔 큐, 후원자 역할 티어(상향 쿼터), 흔한 질의 캐시, 크롤 유휴 시간에 임베딩 사전계산, 무거운 질의는 (후원 시) 더 큰 모델/클라우드로 라우팅 — 단 이건 초저비용·무외부의존과 충돌하니 신중.

**평가:** 가치 高, 구현 高, **리소스/품질 리스크 高, IP 리스크 低.** → 가장 매력적이지만 가장 무겁다. **API/RSS 이후 마지막 단계**로. 단일 슬롯 LLM이 병목이라 쿼터·큐가 전제.

| 1. API | 中 | 低 | 中 | **高**(동적 자가) / 低(정적) | 低 | ② 정적 스냅샷으로만 |

**한 줄 결론:** IP 노출 우려(타당함)는 "**폰에서 인바운드를 받지 말고 결과를 정적으로 push**"로 대부분 해소된다. 그 원칙에 가장 잘 맞는 **RSS를 먼저**, API는 (필요 시) 정적 스냅샷으로, AI봇은 IP 걱정은 없지만 컴퓨트·품질 부담이 커서 쿼터·후원 게이팅을 갖춘 마지막 단계로 둔다.

## 공통 선결 과제(어느 확장이든 하기 전에)

- **크롤 커버리지/품질 안정화** — 확장은 데이터가 신뢰될 때만 의미. 깨진 사이트·셀렉터 감사가 선행(STATUS.md).
- **온디바이스 상시구동·자동복구** — 확장은 "항상 켜져 있음"을 전제로 함.
- **데이터 계약 정리** — API/RSS/봇이 공유할 공통 스키마(학과·공지·요약 필드)를 한 번 확정해두면 세 기능이 같은 소스를 재사용.
