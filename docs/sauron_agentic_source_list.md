
정리하면 두 가지야. **네 서버 한 대로 충분한 작업 규모**라서, 퓨리오사 협력의 가치는 호스팅 비용이 아니라 다른 데 있어. 그리고 이 에이전트의 성능은 소스를 얼마나 많이 모으느냐보다 **평가를 어떻게 하느냐**에서 갈려.

## 1. 냉정한 판단: 퓨리오사 호스팅은 필요 없다

- **처리량은 작아.** 링커리어 하루치가 수백 건이라고 치고, 규칙 필터로 80%를 버리면 LLM에 들어가는 건 하루 100건 안팎이야. 건당 입력 2천 토큰, 출력 300토큰이면 하루 20만 토큰대야(대략적인 추정). 8B~14B급 모델로 네 CMP 170HX에서 하루 몇 분이면 끝나.
- **그래서 "저비용 LLM 호스팅을 해 달라"는 요청은 명분이 약해.** 1인용 서비스에 NPU를 빌려 달라는 요청으로 읽혀.
- **명분이 서는 요청은 따로 있어.** "한국어 공고를 구조화해서 추출하는 실제 워크로드로 RNGD와 GPU를 비교하는 벤치마크를 만들겠다. 결과는 공개하겠다"는 요청이야.
  - 측정 항목: 배치 크기별 처리량, JSON 스키마를 강제한 디코딩 속도, 와트당 토큰, 한국어 추출 정확도.
  - 이러면 **퓨리오사 "LLM Performance" 신입 포지션 지원서가 곧 이 프로젝트**가 돼.
- **로드맵 11월의 대표 프로젝트(추론 병목 하나 직접 고치기)와 합쳐.** 프로젝트를 두 개로 나누면 로드맵의 "하지 않을 것" 중 "새 프로젝트 남발"에 걸려. 이 에이전트의 서빙 레이어를 네 서버에서 최적화하고, 같은 워크로드를 RNGD에서 비교하면 하나로 끝나.

## 3. 설계 조언

**① LLM은 파이프라인 중간 두 군데에만 써.**

```
수집 → 정규화 → 중복 제거 → 규칙 필터 → [LLM 추출] → 자격 판정(규칙) → [LLM 적합도] → 알림 정책
```

- **수집:** 소스마다 어댑터를 따로 만들어. 가능하면 API, RSS, 사이트맵 순으로 쓰고, ETag·If-Modified-Since로 바뀐 것만 가져와.
- **중복 제거:** 같은 대회가 위비티, 링커리어, 콘테스트코리아에 동시에 떠. 키는 정규화한 제목 + 주최 + 마감일로 잡고, 임베딩 유사도로 거의 같은 글도 묶어.
- **규칙 필터:** 카테고리와 키워드로 버려. 영상·마케팅·서포터즈·봉사 같은 것들이야. 이게 LLM 비용을 결정해.
- **LLM 추출:** JSON 스키마를 강제해. 필드는 마감일, 참가 자격(학년·졸업 시기·연령), 개인/팀 여부, 혜택 종류(서류 면제, 상금, 인턴, 인증서)야. vLLM의 guided decoding을 쓰면 형식이 깨질 일이 없어.
- **자격 판정은 LLM이 아니라 규칙으로 해.** "졸업생 불가"는 추출된 필드를 네 프로필과 비교하면 끝나. LLM에게 "이 사람 자격 되나?"를 물으면 틀려.
- **LLM 적합도:** 추출 결과와 프로필을 넣고 등급과 이유 한 줄을 받아. 임베딩으로 1차 순위를 매기고 상위만 큰 모델에 보내는 2단계면 더 싸.

**② 평가가 이 프로젝트의 본체야.**

- 지난 3개월치 공고 200~300건에 **네가 직접 A/B/C/제외 라벨**을 붙여.
- 측정할 건 두 개야. A급 재현율(놓친 A가 몇 개인가)과 A 알림의 정밀도(알림 중 진짜 A가 몇 개인가).
- **비용이 비대칭이야.** 쓸데없는 알림 하나는 몇 초를 버리지만, SK 해커톤 하나를 놓치면 서류와 필기 면제를 통째로 잃어. 그러니 재현율 쪽으로 기준을 기울여.
- 네 문장이 그대로 설계 원칙이 돼: **"지표가 정상이라는 것이 시스템이 정상이라는 뜻은 아니다."** 정확도는 함정이야. 공고의 95%가 제외 대상이라, 전부 제외라고 찍어도 정확도는 95%가 나와. 이게 면접에서 말할 이야기이기도 해.

**③ 피드백 루프**

- "관심 / 지원 / 넘김" 행동이 곧 라벨이야. 쌓이면 few-shot 예시와 프로필 문서를 갱신하는 데 써.
- 파인튜닝은 라벨이 수백 개 쌓이고 few-shot으로 한계가 보일 때 해. 처음부터 하지 마.

**④ "작년 이맘때" 예측 알림**

큰 기회는 매년 돌아와. 작년 공고 날짜를 저장해 두고, 공고가 뜨기 2주 전에 "작년 이 시기에 SK 해커톤 공고, 곧 뜰 가능성 높음"을 먼저 보내. 공고가 뜨는 순간을 기다리는 것보다 이게 강해. 올해 SK 해커톤은 모집 기간이 1주일뿐이었어.

**⑤ 알림 정책**

- 푸시는 새 A급이거나 3일 안에 마감될 때만 보내.
- 나머지는 매일 요약 한 번으로 묶어.
- 주 1회 "넘긴 것 중 다시 볼 만한 것"을 보내서 재현율 누수를 점검해.

**⑥ 법적 리스크는 "누가 쓰느냐"에 달려 있어.**

- **혼자 쓰는 알리미:** robots.txt와 요청 간격만 지키면 리스크가 낮아.
- **"사용자 맞춤형 서비스"로 여러 사람에게 제공:** 이야기가 달라져. 링커리어는 무단 크롤링과 상업적 이용에 법적 책임을 명시하고 있어.
  - 그래서 본문은 저장하지 말고 **메타데이터(제목, 마감일, 링크)와 네가 생성한 요약만** 남겨.
  - 원문은 항상 링크로 보내.
  - API가 있는 소스(사람인, 공공데이터, Greenhouse, 네이버 검색)를 우선해.

## 4. 퓨리오사에 보낼 요청의 뼈대

1. **워크로드 정의.** 한국어 공고를 JSON으로 추출하는 작업이야. 배치 처리라 지연은 신경 안 써도 되고, 처리량과 와트당 토큰이 핵심이야.
2. **이미 한 것.** CMP 170HX에서 같은 워크로드의 기준 수치, RNGD 공개 자료로 세운 가설, 네가 이미 측정한 concurrency 1/2/4 결과(63.4→126.6→231.3 tok/s).
3. **요청.** 일정 기간 RNGD 접근을 달라는 것. 대상 모델은 RNGD가 공식 지원하는 목록 안에서 골라.
4. **돌려줄 것.** 공개 벤치마크 리포트, furiosa-llm과 연동한 오픈소스 코드.
5. **마지막 한 줄.** "LLM Performance 포지션에 관심이 있습니다."

순서는 **SK 해커톤 제출(9/27)과 OPIc이 먼저**야. 이 프로젝트는 로드맵대로 11월에 대표 프로젝트로 시작하면 돼. 그때까지는 내가 걸어 둔 아침 스캔이 임시 알리미 역할을 할 거고, 네가 누르는 관심·지원·넘김 기록은 나중에 Sauron의 첫 평가 라벨로 그대로 쓸 수 있어.
